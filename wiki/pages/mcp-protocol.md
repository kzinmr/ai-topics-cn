# MCP プロトコル：アーキテクチャ、セキュリティ実践、概念関係、および Open Computer Use

MCP（Model Context Protocol / 模型上下文协议）は、Anthropic が提唱した AI Agent と外部ツールを接続するためのオープン標準プロトコル。AI 開発の「USB 規格」とも呼ばれ、モデルとツール間の標準化されたインターフェースを提供する。

> 本ページは 36kr、掘金、V2EX 等の 15+ 件の中国語技術記事・議論を統合・要約したものである。

---

## 一、MCP プロトコルアーキテクチャ概要

### 1.1 MCP とは何か

MCP は、AI アプリケーション（Client）と外部ツール／データソース（Server）の間の標準化された通信プロトコルである。核心のアイデアは、USB 規格のようにツールを「プラグアンドプレイ」方式で動的に発見・呼び出し可能にすること。

**MCP が解決する問題：**
- 各 AI モデル（OpenAI、Claude、文心一言等）の Function Calling 形式が異なる → 統一インターフェースで吸収
- ツールごとに個別の适配コードを書く必要がある → MCP Server として標準化
- Agent とツールの結合度が高い → MCP により疎結合なアーキテクチャを実現

**基本概念：**
- **MCP Server**（サーバー）：ツールやリソースを標準形式で公開する側
- **MCP Client**（クライアント）：AI アプリケーション側、Server に接続してツールを呼び出す
- **Host**（ホスト）：MCP Client を管理するアプリケーション（例：Claude Code、IDE）

### 1.2 三つの基本プリミティブ（三大原语）

MCP は三つの基本プリミティブを通じて、AI Agent の能力を定義する：

#### （1）Tools（ツール） — AI の「手」

- 外部関数や API を MCP 標準形式でラップ
- スキーマ（JSON Schema）で入出力を定義
- Agent が自動で発見し、呼び出すことができる
- 例：天気照会、データベースクエリ、ファイル操作

#### （2）Resources（リソース） — 構造化されたコンテキスト注入

- ファイル、データベーススキーマ、API ドキュメント等のデータソースを標準化
- Agent が「読める」形式でコンテキストを提供
- URI で一意に識別
- 例：プロジェクトのドキュメント、コードベースの構造情報

#### （3）Prompts（プロンプト） — 再利用可能なインタラクションテンプレート

- 事前定義されたプロンプトテンプレート
- 特定のワークフローやタスクパターンをカプセル化
- 変数埋め込みをサポート
- 例：コードレビュー用テンプレート、デバッグ用テンプレート

### 1.3 传输机制（トランスポートメカニズム）

MCP は複数の通信方式をサポートし、ローカルからクラウドまで柔軟なデプロイが可能：

| 方式 | 説明 | 適用シーン |
|------|------|-----------|
| **STDIO** | ローカルプロセス間通信 | 最も一般的。Claude Code 等が採用 |
| **Streamable HTTP** | HTTP ベースのストリーミング | リモート MCP Server、クラウドデプロイ |
| **SSE / WebSocket** | サーバープッシュ型リアルタイム通信 | リアルタイム監視、ストリーミングデータ |

**STDIO 传输**：シンプルで効率的なローカル通信方式。MCP Server がサブプロセスとして起動され、標準入出力を通じて JSON-RPC メッセージを交換。セキュリティ面ではサンドボックス化が容易。

**Streamable HTTP 传输**：分散環境向けの標準化されたリモート通信方式。ステートフルなセッション管理、接続の持続性をサポート。

### 1.4 MCP のワークフロー

```
┌─────────────┐     JSON-RPC     ┌─────────────┐
│  MCP Host   │ ────────────────▶ │  MCP Client │
│ (Claude Code│                   │   Manager   │
│  / IDE)     │ ◀───────────────  │             │
└─────────────┘     response      └──────┬──────┘

                              tools/list │
                              resources/ │
                              prompts/   │

                               ┌─────────────┐
                               │  MCP Server │
                               │  (ツール/   │
                               │   リソース) │
                               └─────────────┘
```

## 二、本番環境セキュリティ実践

### 2.1 OWASP MCP Top 10 脆弱性

MCP プロトコルを使用する際、以下のセキュリティリスクに注意する必要がある：

> 📌 出典：深度解析 MCP 协议：架构设计与生产级安全实践（掘金 / 预知同行）

| # | 脆弱性 | 説明 |
|---|--------|------|
| 1 | **プロンプトインジェクション** | 悪意ある入力が Agent の意図を改ざん |
| 2 | **権限昇格** | MCP Server 経由で過剰な権限を取得 |
| 3 | **データ漏洩** | 機密データが Tool/Resource 経由で露出 |
| 4 | **不適切な認可** | ツール呼び出しの認証・認可不備 |
| 5 | **信頼できないコンテンツ** | 外部からの入力検証不足 |
| 6 | **リソース枯渇** | 無限ループや過剰な API 呼び出し |
| 7 | **プロセス分離の不備** | サンドボックス化されていない実行環境 |
| 8 | **構成管理の不備** | 秘密情報のハードコーディング |
| 9 | **サプライチェーン攻撃** | サードパーティ MCP Server の信頼性 |
| 10 | **監査・ロギング不足** | アクションの追跡可能性の欠如 |

### 2.2 本番環境デプロイのベストプラクティス

#### （1）最小権限の原則（最小権限）
- 各 MCP Server に必要最小限の権限のみ付与
- Agent ごとに異なる Skill セットを割り当て、権限隔離を実現
- ファイルシステムへのアクセスは読み取り専用で開始

#### （2）入力検証（入力検証）
- すべての外部入力を厳密に検証
- JSON Schema による厳密なパラメータ定義
- プロンプトインジェクション対策として入力サニタイズ

#### （3）サンドボックス化
- MCP Server は分離された環境で実行
- Docker コンテナや systemd サービスでプロセス分離
- Claude Code の場合、CLI レベルのセキュリティサンドボックスとコマンドインターセプトメカニズムを採用

#### （4）監査とロギング
- すべてのツール呼び出しをログ記録
- Agent の意図と実際のアクションの比較検証
- 異常なパターン検知とアラート設定

#### （5）セキュリティパッチ管理
- LangChain 等、関連フレームワークの CVE 修正を即座に適用
  - 例：CVE-2026-4539（PromptTemplate の `str.format_map` による二次テンプレート解析脆弱性）
- 依存関係の定期的な更新と脆弱性スキャン

## 三、Prompt / Agent / Function Call / Skill / MCP の概念関係

> 📌 出典：Prompt、Agent、Function Call、Skill、MCP，傻傻分不清楚？（掘金 / 苏三说技术）

### 3.1 五層構造：AI アプリケーション開発の「五階建て」

これらの概念は互いに排他的ではなく、**層状的に積み上がる**関係にある：

```
                    ┌─────────────────────┐
    Layer 5: MCP    │  統一ツール接続の    │  ← AI 世界の「USB 規格」
                    │  「世界語」          │
                    ├─────────────────────┤
    Layer 4: Skill  │  専門知識を          │  ← AI の「職業資格証書」
                    │  カプセル化した      │
                    │  「スキルパック」    │
                    ├─────────────────────┤
    Layer 3: Agent  │  自律的意思決定を    │  ← AI の「脳」
                    │  行う「知能体」      │    （思考・計画・実行）
                    ├─────────────────────┤
    Layer 2: Func   │  外部ツールを        │  ← AI の「手」
           Call     │  呼び出す能力        │
                    ├─────────────────────┤
    Layer 1: Prompt │  AI への指示         │  ← AI との「共通語」
                    │  （プロンプト）      │
                    └─────────────────────┘
```

### 3.2 各概念の核心定義

| 概念 | 一言定義 | 核心作用 | 例え |
|------|---------|---------|------|
| **Prompt** | AI への指示 | AI に何をすべきか伝える | レストランでの注文 |
| **Function Call** | 外部ツール呼び出し | AI に「行動する」能力を付与 | 锤子、螺丝刀、扳手 |
| **Agent** | 自律的意思決定システム | 複雑なタスクのクローズドループ | 「脳」を持った完全なシステム |
| **Skill** | 専門知識のパック | 分野固有の知識とベストプラクティスを固定化 | 工具箱 + 操作マニュアル |
| **MCP** | 統一ツール接続プロトコル | 全 AI に同一インターフェースを提供 | USB 規格 |

### 3.3 Function Call vs Skill

| 次元 | Function Call | Skill |
|------|--------------|-------|
| 本質 | 単一能力 | 能力集合 + 知識 |
| 粒度 | アトミック操作 | ビジネスモジュール |
| ツール包含 | それ自体がツール | 複数のツールを含む |
| 知識包含 | 含まない | 分野知識とベストプラクティスを含む |
| コード形式 | 単一 `@Tool` メソッド | 複数の `@Tool` + システムプロンプト |
| 应用场景 | 天気照会、メール送信等の単一操作 | フロントエンド開発、運用管理、財務分析等专业分野 |

**関係式：** `Function Call + 分野知識 + ベストプラクティス = Skill`

### 3.4 MCP と Skill の関係

MCP と Skill は**補完的**な関係：
- **MCP** は「どう接続するか」を解決 — ツール呼び出しプロトコルの標準化
- **Skill** は「何を接続するか」を解決 — 専門知識とツール集合のカプセル化

典型的なアーキテクチャ：Agent が MCP 経由で様々な Skill が公開するツールを呼び出す。これにより、基盤ツールがどう変化しても Agent のコード変更不要。

### 3.5 学習の優先順位

> 「まず **Prompt** から始めよ。これは全 AI アプリケーションの基礎。Prompt を理解したら、次に Function Call に触れ、そして簡単な Agent の構築を試みる。Skill と MCP については、まず概念を理解し、アプリが複雑になって複数 Agent の協調が必要になった段階で深く学べばよい。」

## 四、Open Computer Use プロジェクト

> 📌 出典：开源 Open Computer Use（V2EX / IterX）

### 4.1 プロジェクト概要

**open-computer-use** は、Computer Use 能力をオープンソースで実装し、MCP プロトコルにラップしたプロジェクト。全ての AI Agent や MCP Client が迅速に呼び出し可能。

**背景：**
- OpenAI が Codex Computer Use を発表
- Accessibility API を利用した**非抢占式 CUA 能力** の実現可能性を示した
- これに触発され、オープンソース版の复刻が決定

### 4.2 核心機能

- **macOS 上の Computer Use 能力** をサポート
- **MCP 協議** に準拠したサーバーとして包装
- **全ての AI Agent / MCP Client** から呼び出し可能
- **Accessibility API** ベース — 画面の占有（grab）なしで操作

### 4.3 技術的意義

Open Computer Use は、MCP プロトコルの**実用性の良い例**を示している：
- Computer Use という特定の能力を MCP Server として標準化
- 任意の MCP 対応 Agent（Claude Code、ChatGPT Desktop 等）からシームレスに利用可能
- プロトコルの「プラグアンドプレイ」思想を体現

## 五、コミュニティの声：MCP の現実

### 5.1 MCP への批判と依存

V2EX での議論（「大家都在嫌弃 MCP 的时候我竟然发现有点离不开它」）は、MCP の現実的な課題と価値を浮き彫りにしている：

**批判の声：**
- 「過剰設計に見える」「書きにくい」「使いにくい」
- コミュニティでは API や CLI での代替が議論されている

**しかし、代替が難しい理由：**
- **MCP により Agent の意図をより良く感知できる**
- Skill や Prompt だけでは Agent の一貫した動作を保証できない（特に長時間実行時）
- 呼び出し戻り値に Prompt を注入する方法も限界がある
- MCP は**構造化されたインターフェース**を提供し、Agent とツール間の明確な契約を確立

### 5.2 MCP サーバーの生態系

掘金 の記事（「别再裸用 Claude Code 了！32 个亲测Skills + 8 个 MCP，开发效率直接拉满！」）は、実践的な MCP の活用を示している：

- 開発効率向上のための MCP サーバー群
- 実測済みの Skills との組み合わせ
- Claude Code 等の Coding Agent との連携

### 5.3 MCP ライフサイクル管理

Claude Code のソースコード解析（36kr 報道）によれば、print.ts 関数（3167行、486分岐、嵌套深度12層）には、以下が含まれる：
- Agent の実行ループ
- SIGINT 中断処理
- レート制限ロジック
- AWS 認証
- **MCP ライフサイクル管理**
- プラグイン読み込み
- モデル切り替え
- 中断回復メカニズム

これは MCP が単なるプロトコルではなく、AI Agent の**コアインフラストラクチャ**として深く組み込まれていることを示している。

## 六、まとめ

MCP（Model Context Protocol）は、AI Agent 開発において以下の価値を提供する：

1. **標準化** — モデル間の差異を吸収し、「USB のように」ツールを接続
2. **疎結合** — Agent とツールを分離し、柔軟な拡張を可能に
3. **セキュリティ** — 構造化されたインターフェースにより、権限制御と監査を容易に
4. **エコシステム** — 誰でも MCP Server を公開でき、全ての Agent が利用可能

AI アプリケーション開発の五層構造（Prompt → Function Call → Agent → Skill → MCP）において、MCP は**基盤となる接続層**として、上位層の柔軟性と拡張性を支える。

> 「MCP がなければ AI は道具を使えない。MCP こそが AI の手足を世界に繋ぐ規格である。」
