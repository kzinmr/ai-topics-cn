## 一、中国AI大模型发布格局

### GLM-5（智谱AI）

[[entities/zhipuai]] 于2026年2月发布 **GLM-5**，是国产大模型的重要里程碑：

- **参数规模**：744B参数MoE架构（激活参数40B），相较前代GLM-4.7的355B实现大幅跃升
- **预训练数据**：从23T提升至28.5T tokens
- **性能表现**：SWE-bench-Verified得分 **77.8**，超越Gemini 3 Pro，与闭源旗舰 Claude Opus 4.5 持平
- **开源策略**：完全开源，部署于 GitHub ([zai-org/GLM-5](https://github.com/zai-org/GLM-5))、HuggingFace、ModelScope 多平台
- **核心定位转变**：从"Vibe Coding"一句话生成升级为 **Agentic Engineering（智能体工程）**——具备系统架构能力，可独立完成长任务、多步骤开发

GLM-5开发代号"**Pony**"，据推测与即将到来的马年有关。在OpenRouter周排行榜和OpenClaw调用量榜单中长期霸榜前列。

**实战表现**：开发者反馈其在复杂系统搭建、多Bug并行修复、浏览器自动化（Playwright MCP调用）等场景中表现稳健，"一次修复成功率高"，且在修改代码时不会"拆东墙补西墙"。

### Kimi K2.6（月之暗面）— 2026年4月アップデート

[[entities/kimi-k2-6|Kimi K2.6]] は2026年4月にアップデートされ、**推論能力が大幅に改善**された。

- **推論能力**: 長コンテキストと実世界タスクで「人間のようなエージェント」行動。Chain-of-thought構造は安定維持
- **価格**: 単価コストが21→27へ（合理化の範囲内）
- **非推論モード**: 単純タスクは数千トークンで処理、複雑タスクは20K-30Kトークンに拡張
- **推論モード**: 推論チェーンが过长（80Kトークン超）になり、ベンチマーク制限で評価が不完全な場合も

### DeepSeek V4 Flash — 低コスト層の拡大

V4のFlash版はMid/Mid-16 tiersを提供。DeepSeekの「**低コスト・低遅延**」ポジショニングを明確化:

- Flashは「**より多くのユーザーに手が届く低コスト・低遅延の選択肢**」
- 価格戦略はV4 Proと階層化され、幅広いアクセスを確保
- Moonshot（Kimi）やGLMも低コスト・低遅延版を追加。**低コスト推論は全メーカーの競争軸**に

> **ChinAI #356** — [DeepSeek as Road Builder [修路人]](https://substack.com/app-link/post?publication_id=2660&post_id=195527792)

### DeepSeek V4 技術詳細（Zhihu Frontier Weekly 2026-04-27追記）

Zhihu Frontier Weeklyは、DeepSeek V4の詳細な実測分析を提供している。主要な発見：

- **V4 Proのコーディングベンチマーク**: SWE-bench Verified 92.3%がClaude Opus 4.6 (80.9%)を大幅上回る
- **V4 Proの動作特性**: 深い推論→1パスコード生成→自己テストの厳格な実行ループ。低レベルエラーが大幅減少。max tierは高tierよりツール呼び出しfreqが~60%増加、ファイル読深度も~60%増加
- **V4 Flash**: 中小規模モデルと同等のサイズで高速・低コスト化。1ショット課題では高〜完璧の分散が大きい。トークン消費は期待より多いが、コストパフォーマンスは依然として強力
- **低コスト推論は全メーカーの競争軸**: Moonshot（Kimi）、GLM、StepFunなどが低コスト・低遅延版を追加

### Kimi K2.5（月之暗面）

[[entities/moonshot|月之暗面 (Moonshot AI)]] 的 **Kimi K2.5** 在OpenClaw调用请求量榜单中 **长期霸榜第一**，大幅领先 Gemini 3：

- 在开发者社区中口碑极佳，被评价为"用了就回不去"
- 与Claude Code集成方案成熟，支持标准Anthropic兼容接口
- 日常开发场景中效率不输Claude和OpenAI官方模型

> [!warning] 月之暗面面临的挑战
> 36氪报道指出，月之暗面"要翻的山不止一座，要花的钱不止一点点"。公司面临持续的算力成本压力和商业化挑战。[[source:36kr]]

### DeepSeek（深度求索）

[[entities/deepseek]] 在2026年4月传出 **首次外部融资** 消息：

- **估值**：不低于100亿美元
- **融资规模**：计划至少3亿美元
- 此前公司一直坚持"不融资"策略，此次转变被市场解读为需要更大规模的算力投入

## 二、开发者工具生态

### AI编码工具的范式转变

2026年中国开发者社区正经历从 **Vibe Coding（氛围编程）** 向 **Agentic Engineering（智能体工程）** 的范式转换：

#### Vibe Coding 概念

- 核心理念：通过自然语言描述需求，AI自动生成代码
- 涵盖基础概念：AI、LLM、模型参数、训练与推理、Fine-tuning、Token计费
- 局限：适合快速原型和Demo，但在复杂系统工程中表现不足

> Vibe Coding的兴起反映了AI编码工具从"辅助写代码"向"替代写代码"的演进路径。[[source:juejin]]

#### Agentic Engineering 新范式

以GLM-5为代表的新一代AI编码工具展现出不同的工作模式：

1. **Plan Mode（规划模式）**：先制定详细计划，经开发者批准后再执行
2. **工具链调用**：自主使用浏览器自动化（Playwright MCP）、终端命令、文件操作等
3. **自我反思**：在长任务中不断验证、修正
4. **多步骤编排**：可独立处理包含多个子任务的复杂工程

### Claude Code 生态

Claude Code 已成为中国开发者社区的核心工具之一，但存在显著问题：

- **账号封锁**：国内开发者账号频繁被封
- **连接超时**：访问不稳定，"花了数千Token喂上下文，一个timeout就没了"
- **订阅限制**：OpenClaw等工具不再支持Plus会员订阅

#### 国产模型替代方案

开发者普遍采用以下策略绕过限制：

```bash
# GLM 接入 Claude Code
export ANTHROPIC_BASE_URL=https://open.bigmodel.cn/api/anthropic
export ANTHROPIC_MODEL=GLM-4.7

# Kimi 接入 Claude Code
export ANTHROPIC_BASE_URL=https://api.moonshot.cn/anthropic
export ANTHROPIC_MODEL=kimi-k2.5
```

使用 **claude-code-router** 工具可一键切换模型：

```bash
ccr use kimi    # 切换到 Kimi
ccr use glm     # 切换到 GLM
ccr use claude  # 切回 Claude 官方
```

### "无编辑器/CLI"编程讨论

V2EX社区关于纯CLI聊天的编程方式存在明显分歧：

> "看不到代码，心里感觉虚的很。提供上下文给AI时，没办法精确关联到文件第几行。" — [[source:v2ex]]

核心痛点：
- 代码不可见导致信任缺失
- 上下文关联困难
- 复杂任务难以精确控制

但同时，许多开发者报告通过Plan Mode + 国产模型组合已能高效完成实际开发任务。

### Skills 与 MCP 生态

- **Claude Skills**：社区涌现大量自定义Skill，用于扩展编码助手能力
- **MCP（Model Context Protocol）**：作为标准化协议，被用于浏览器自动化、数据库操作等工具集成
- **Prompt / Agent / Function Call 概念辨析**：社区讨论表明这些概念经常被混淆，需要更清晰的边界定义

### 阿里 CodingPlan 服务

阿里云推出全新CodingPlan服务，整合Qwen-3.5、Kimi-K2.5和GLM-4.7等国内顶尖AI编程模型：

- **计费模式**：按请求次数计费，替代传统Token计费
- **优势**：解决Token成本不可预测的问题
- **意义**：标志云厂商开始将多模型集成作为标准化服务

## 三、产业落地模式

### OpenClaw + 电商后台实践

将OpenClaw接入电商平台后台的实践揭示了AI落地的核心挑战：[[source:juejin]]

#### 典型应用场景
- 订单异常汇总与排查建议
- 运营数据查询与后台入口串联
- 库存/活动/商品状态冲突检查
- 日志和告警噪音过滤
- 重复性SOP自动化处理

#### 核心教训

1. **状态系统问题 > 语义理解问题**
   > "电商后台里的很多问题，本质上不是语义理解问题，而是状态系统问题。"

2. **"半对半错"比"完全不会"更危险**
   - Agent可能知道查库存，但不知道活动库存与可售库存口径不同
   - 可能读懂订单状态，但未意识到售后单已锁住后续流程

3. **工程化挑战 > 模型能力挑战**
   - 服务超时、接口字段变更、环境差异等问题频发
   - "所有问题都长得像模型问题"是最危险的错觉

#### 落地原则（重新校准后的AI Agent价值观）

- 知道自己什么时候能答
- 知道自己什么时候该停
- 知道什么时候必须交还人工
- 全程留痕，方便回放和复盘
- 输出有依据，而非"只像那么回事"

> **结论**："把AI真正接进业务后台之后，最深的体会不是它有多聪明，而是只有当资源、链路、边界和成本都被认真处理过，智能体才有资格谈落地。"

### 荣耀AI端侧战略

[[entities/honor|荣耀 (Honor)]] AI专家李向东在专访中阐述了端侧AI的方向：[[source:36kr]]

**AI手机三要素**：
1. **Agent自动执行** — 不仅是语音助手，而是能主动完成任务
2. **个人化全局记忆** — 基于用户习惯的长期学习
3. **多模态感知和主动服务** — 结合视觉、语音、传感器的综合理解

> "端侧AI方向还没收敛，但AI手机是最好的载体。"

### NotebookLM 与写作工具生态

V2EX用户讨论指出，Google NotebookLM虽然好用，但用户需求已从"与AI对话"转向"写作创作"：[[source:v2ex]]

- 富文本编辑器集成全网素材搜索
- AI辅助修改、思维导图生成
- 自动生成信息图（利用nanobanana等模型能力）
- 反映从"信息获取"向"内容创作"的工具需求转移

## 四、算力基础设施趋势

### 国产算力芯片集群

GLM-5发布后的一个重要信号：

> "官方正在紧急扩容，而且重点是，这次接入的是 **国产芯片的万卡集群**。" — [[source:juejin]]

这标志着从芯片到模型、从底层算力到上层应用，中国正在构建 **完全自主的AI技术栈**。

### 弹性算力平台崛起

OpenClaw电商后台实践中，开发者将资源调度迁移到 **蓝耘GPU算力平台**：

- **按秒计费** 模式显著降低试错成本（节省约30%）
- 适合阶段性实验、验证、回放、压测等碎片化工作流
- 解决"资源空转"这一AI开发中的隐性成本

### MaaS（模型即服务）平台

MaaS平台的价值在于降低"接模型"的摩擦：

- 避免反复处理模型接入、接口切换、能力对比、封装适配
- 让开发者注意力回归业务逻辑和系统设计
- 与CodingPlan服务结合，形成从模型到应用的全链路服务

### 算力成本结构变化

| 成本类型 | 传统模式 | 2026年新趋势 |
|----------|----------|-------------|
| 计费方式 | Token计费 | 按请求/按秒计费 |
| 算力来源 | 集中式云服务 | 弹性GPU + MaaS |
| 芯片策略 | 依赖进口GPU | 国产万卡集群 |
| 试错成本 | 高 | 降低（弹性调度） |

## 六、趋势展望

### 2026年关键趋势

1. **开源模型崛起**：GLM-5等开源模型在性能上逼近闭源旗舰，降低开发门槛
2. **从Vibe Coding到Agentic Engineering**：AI编码工具从"生成代码"升级为"构建系统"
3. **国产算力自主化**：国产芯片万卡集群 + MaaS + CodingPlan 形成完整技术栈
4. **AI落地务实化**：从追求"模型有多聪明"转向"系统能不能长期跑稳"
5. **计费模式革新**：从Token计费转向按请求/按秒计费，降低AI使用门槛
6. **端侧AI探索**：AI手机作为个人AI入口的潜力被重新评估

### 风险与挑战

- 月之暗面等公司的持续融资压力和商业化路径
- Claude Code等国外工具在国内的可用性限制
- AI Agent在复杂业务系统中的"半对半错"风险
- 算力成本的可控性与资源利用率优化
