## 1. RAG 技术概述

**RAG（Retrieval-Augmented Generation，检索增强生成）**是将 LLM 的生成能力与外部知识库检索相结合的架构模式。其核心流程为：

```
用户查询 → Embedding 模型 → 向量数据库检索 Top-K → 注入上下文 → LLM 生成回答
```

截至 2026 年 4 月，中文 AI 社区对 RAG 的讨论出现了一个重要转向：从「如何构建 RAG 系统」转向「**RAG 是否过时**」（RAG 过时了吗？）。36kr 明确指出：

> "RAG 并未过时，但需要进化"

核心驱动因素包括：
- **LLM 上下文窗口持续扩大**（部分模型已突破百万 Token），但静态知识库注入仍面临精度瓶颈
- **Embedding 模型的语义理解局限**：向量余弦相似度无法完全捕获复杂逻辑推理关系
- **RAG 系统安全问题凸显**：检索结果污染、间接 Prompt Injection、知识库数据泄漏等

在此背景下，2026 年的 RAG 技术生态呈现出两条并行发展路线：

| 路线 | 特征 | 代表技术 |
|------|------|----------|
| **向量 RAG 进化** | 优化 Embedding、混合检索、重排序 | GraphRAG、Agentic RAG、Multi-Modal RAG |
| **无向量 RAG** | 抛弃 Embedding，以 LLM 推理驱动检索 | PageIndex |

## 2. 向量数据库五大选型对比

2026 年向量数据库市场已形成五大主流产品的竞争格局。以下从架构特性、适用场景、中文生态三个维度进行深度对比。

### 2.1 Milvus

| 维度 | 详情 |
|------|------|
| **开发方** | Zilliz（中国） |
| **许可证** | Apache 2.0 |
| **编程语言** | Go + C++ |
| **部署模式** | 分布式 / 单机（Milvus Lite） |
| **核心特性** | 大规��分布式、Kubernetes 原生、多向量索引（HNSW、IVF、DiskANN） |

**适用场景：**
- 企业级大规模向量检索（亿级以上数据量）
- 需要完整权限管理、多租户隔离
- 中国境内合规部署要求

**中文生态优势：**
- 中国本土企业，中文文档、社区支持最完善
- 与阿里云、腾讯云等国内云厂商深度集成
- 国内开发者社区（掘金、知乎）讨论热度最高

**局限：**
- 部署运维复杂度高
- 单机轻量场景过度设计

### 2.2 Qdrant

| 维度 | 详情 |
|------|------|
| **开发方** | Qdrant（德国） |
| **许可证** | Apache 2.0 |
| **编程语言** | Rust |
| **部署模式** | 分布式 / 单机 / 云服务 |
| **核心特性** | 高性能过滤查询、Payload 机制、HNSW 索引 |

**适用场景：**
- 需要向量检索 + 结构化过滤的组合查询
- 对性能和资源效率要求极高
- 推荐系统、语义搜索中间层

**技术优势：**
- Rust 实现，内存安全、零 GC 停顿
- 混合查询（向量 + 标量过滤）性能领先
- API 设计简洁，集成门槛低

### 2.3 Weaviate

| 维度 | 详情 |
|------|------|
| **开发方** | Weaviate（荷兰） |
| **许可证** | BSD-3 |
| **编程语言** | Go |
| **部署模式** | 分布式 / 云服务（WCS） |
| **核心特性** | GraphQL API、模块化架构、内置向量化模块 |

**适用场景：**
- 已有 GraphQL 技术栈的团队
- 需要语义搜索 + 知识图谱融合
- 多模态向量检索

**技术优势：**
- 模块化设计，可灵活接入不同 Embedding 模型
- 内置文本向量化、图像向量化等模块
- GraphQL 原生支持，API 设计优雅

**局限：**
- 模块依赖可能导致部署复杂度增加
- 中文社区资源相对较少

### 2.4 Chroma

| 维度 | 详情 |
|------|------|
| **开发方** | Chroma（美国） |
| **许可证** | Apache 2.0 |
| **编程语言** | Python |
| **部署模式** | 嵌入式（进程内） / 服务端 |
| **核心特性** | 极简 API、Python-first、零配置 |

**适用场景：**
- 原型开发、PoC 验证
- 轻量级 RAG 应用
- 个人项目、学术实验

**技术优势：**
- `pip install chromadb` 即可使用，五分钟上手
- 与 LangChain、LlamaIndex 无缝集成
- 进程内模式无额外运维成本

**局限：**
- 分布式能力有限，不适合生产级大规模部署
- 高级功能（如多租户、细粒度权限）欠缺

### 2.5 Pinecone

| 维度 | 详情 |
|------|------|
| **开发方** | Pinecone（美国） |
| **许可证** | 商用（闭源） |
| **部署模式** | 全托管云服务（SaaS） |
| **核心特性** | Serverless、自动扩缩容、托管索引管理 |

**适用场景：**
- 不想运维基础设施的团队
- 需要弹性扩展的生产环境
- 预算充足、追求开箱即用

**技术优势：**
- 零运维，全托管
- Serverless 架构自动处理扩缩容
- 成熟的 SDK 和文档

**局限：**
- **中国合规风险**：数据存储在海外，不符合中国数据本地化法规
- 闭源，无法自建
- 长期使用成本高于自托管方案

## 3. PageIndex — 无向量 RAG 新范式

### 3.1 核心理念

**PageIndex** 是 2026 年出现的一种创新性 RAG 框架，其核心突破在于：**完全抛弃向量 Embedding**，改用 LLM 自身的推理能力来评估文档页面的相关性。

> "PageIndex 是一个创新的、无向量（Vectorless）且基于推理（Reasoning-based）的检索增强生成（RAG）框架。"
> — 掘金（Cosolar），2026-04-18

### 3.2 与传统 RAG 的对比

| 维度 | 传统 RAG | PageIndex |
|------|----------|-----------|
| **检索方式** | 向量余弦相似度 | LLM 推理评估 |
| **索引结构** | 高维向量数据库 | 结构化页面索引 |
| **文档处理** | 分块（Chunking）→ 向量化 | 页面级结构保留 |
| **语义理解** | Embedding 模型决定上限 | LLM 推理能力决定上限 |
| **信息损失** | Chunking 导致上下文断裂 | 页面为单位，上下文完整 |
| **基础设施** | 需要向量数据库 | 无需向量数据库 |

### 3.3 工作流程

```
长文档 → 页面级结构化索引（保留文档层次）
                          ↓
用户查询 → LLM 推理评估页面相关性 → 定位目标页面
                          ↓
               提取完整页面内容 → LLM 生成回答
```

关键创新点：
1. **页面级检索**：保留文档的原始结构（章节、页面），而非暴力切分
2. **推理驱动**：利用 LLM 的逻辑推理能力判断页面相关性，而非向量距离
3. **零向量依赖**：不需要 Embedding 模型，不需要向量数据库

### 3.4 优势分析

- ✅ **避免 Chunking 信息损失**：传统 RAG 的文档切分会破坏上下文连贯性，PageIndex 以页面为粒度保留完整语义
- ✅ **推理质量更高**：Embedding 的余弦相似度只能捕获浅层语义近似，LLM 推理可以处理复杂的逻辑关联
- ✅ **基础设施简化**：无需部署和维护向量数据库
- ✅ **调试更直观**：页面级索引比向量空间更容易理解和排查

### 3.5 局限与挑战

- ⚠️ **推理成本高**：每次检索都需要调用 LLM 进行推理评估，相比向量检索（毫秒级）成本显著更高
- ⚠️ **延迟问题**：LLM 推理引入的延迟难以满足实时搜索场景
- ⚠️ **大规模可扩展性**：面对百万级页面时，推理评估的吞吐量成为瓶颈
- ⚠️ **模型依赖**：检索质量高度依赖底层 LLM 的推理能力

### 3.6 适用场景

| 场景 | 适用性 | 原因 |
|------|--------|------|
| 技术手册查询 | ✅ 高度适用 | 文档结构清晰，页面粒度合理 |
| 法律文档分析 | ✅ 高度适用 | 推理需求高，准确性优先 |
| 学术论文检索 | ✅ 适用 | 结构化程度高 |
| 客服对话系统 | ⚠️ 部分适用 | 延迟敏感场景需权衡 |
| 大规模向量检索替代 | ❌ 不适用 | 成本和延迟无法接受 |

## 4. RAG 的进化方向：2026 技术全景

### 4.1 GraphRAG

将知识图谱（Knowledge Graph）与 RAG 结合，通过图结构捕获实体间的关系，提升复杂查询的检索精度。

- **优势**：关系感知推理、多跳检索、可解释性强
- **挑战**：知识图谱构建成本高、维护复杂

### 4.2 Agentic RAG

RAG 不再是简单的「检索 → 注入 → 生成」流水线，而是由 Agent 自主决定：
- 检索什么（动态查询改写）
- 从哪里检索（多源选择）
- 如何整合（多轮推理验证）

这是 36kr 提出的「RAG 进化」方向的核心——从被动检索到主动知识获取。

### 4.3 Multi-Modal RAG

将检索范围从纯文本扩展到图像、音频、视频等多模态数据：

```
文本查询 → 多模态 Embedding → 跨模态检索 → 多模态上下文 → 生成回答
```

### 4.4 混合检索架构（Hybrid Retrieval）

2026 年实践中最成熟的方案：**向量检索 + 关键词检索 + 重排序（Reranking）**

- 向量检索：捕获语义相似性
- 关键词检索：保证精确匹配
- Reranker 模型：对候选结果进行精排序

### 4.5 技术路线对比

| 技术路线 | 向量依赖 | 推理依赖 | 适用规模 | 延迟 | 精度 |
|----------|----------|----------|----------|------|------|
| 传统 RAG | ✅ | ❌ | 大规模 | 低 | 中 |
| GraphRAG | ✅ | 部分 | 中大规模 | 中 | 高 |
| Agentic RAG | ✅ | ✅ | 中等 | 中-高 | 高 |
| PageIndex | ❌ | ✅ | 中小规模 | 高 | 极高 |
| 混合检索 | ✅ | 部分 | 大规模 | 中 | 高 |

## 5. 中国语境的部署考量

### 5.1 数据合规

中国企业部署 RAG 系统必须考虑《数据安全法》和《个人信息保护法》的要求：

- **Pinecone 等海外托管服务**存在数据出境风险，不适合处理敏感数据
- **Milvus（Zilliz 中国）**在国内合规方面具有天然优势
- 自建开源方案（Qdrant、Chroma）可完全控制数据流向

### 5.2 中文语义挑战

中文 RAG 系统面临特有的技术难题：
- **分词粒度**：中文无天然词界，Chunking 策略需要适配
- **语义歧义**：同音字、一词多义导致 Embedding 精度下降
- **知识更新**：中文语料库时效性要求更高

### 5.3 成本优化实践

中文社区总结的 RAG 成本控制经验：

1. **分级索引**：热点数据用向量检索，冷数据用 PageIndex 按需推理
2. **缓存层**：高频查询结果缓存，避免重复检索
3. **模型降级**：简单查询用轻量 Embedding 模型，复杂查询用大模型推理
4. **混合架构**：向量检索 + 关键词检索 + 规则过滤，减少对纯向量方案的依赖
