# CLI vs MCP vs GUI — エージェント時代のインタラクションパターン

2026年4月、開発者の叶小钗（Yè Xiǎochāi）が発表した長文考察記事。CLI・MCP・GUI・Skillsの関係性を体系的に整理し、「エージェント時代におけるシステム能力の暴露形式」を論じた。

> **結論**: CLIは唯一の答えではないが、**現時点で最良の答え**になりつつある。Agentは天然、組み合わせ可能・テキスト化可能・スクリプト化可能・監査可能なインターフェースを呼び出すのに適しており、CLIはまさにそれを満たす。

## 核心となる3つの問い

1. **Agentにとって、どのようなインターフェースが最も理解・実行しやすいか？**
2. **エージェントが作業を完了するために必要な前置作業は何か？**
3. **GUI・CLI・MCPはそれぞれどのレイヤーの問題を解決しているか？**

## CLI・MCP・GUI・Skillsの役割分担

| レイヤー | 解決する問題 | 具体例 |
|---------|------------|--------|
| **Function Calling** | モデルが**呼び出し意図**をどう表現するか | tool schema、JSON出力 |
| **MCP** | ツールをどう**統一接入**するか | ツール登録、schema暴露、host発見 |
| **Skills** | タスクをどう**計画・組織化**するか | SOP、ワークフロー定義 |
| **CLI** | 能力をどう**実行形態**で暴露するか | コマンド、サブコマンド、パラメータ |

### Function Calling = モデル側の呼び出しプロトコル

モデルとホストプログラム間のコミュニケーション方式。モデルは構造化された関数定義に基づいて呼び出しを生成する。

### MCP = システム側の接入プロトコル

MCPが解決するのは「モデルがどうツールを呼ぶか」ではなく、**「ツール自体をどう大規模・統一にエージェントシステムに接入するか」**。

- ツールの登録方法
- schemaの暴露方法
- hostがツールを発見する方法
- 異なるAgent/モデルが同一バッチのツールを再利用する方法

> MCPは**tool integration bus**。エージェントプラットフォームの生態系拡張的重要组成部分。

### Skills = 実行パスの組織化

Skillsは`Tools定義の過多によるコンテキスト爆発`を按需ロードで解決し、SOP/Workflowをプロンプトに装入してタスク実行の安定性を大幅に向上させる。

Skillsの書き方：
```
1. どのアクションを先に実行するか
2. 次にどのアクションを実行するか
3. 失敗した場合、どのアクションに切り替えるか
4. 結果が大きすぎる場合、どのフィールドを取得するか
5. 最終的にどの構造で出力するか
```

### CLI = 能力の実行形態

CLIが解決するのは「ツールをどう接入するか」でも「どう計画するか」でもなく、**「システム能力自体が最終的にどのような形態で暴露され、人間とAgentが実際に実行するか」**。

CLIの価値：**SkillsにとってMCPより使いやすいアクション層を提供する**。

CLIの世界では：
1. 1つのコマンド = 1つのアクション
2. 1つのサブコマンド = アクションの細分化
3. 1組のパラメータ = アクションの境界

## CLI改造の本質

CLI改造の本質は、GUIをコマンドラインに置き換えることではなく、**元々GUIの裏に埋もれていた能力を一連の実行可能なアクションとして再暴露すること**。

### 仮想钉钉（DingTalk）のCLI改造例

**1. 照会系アクション**
```bash
dingtalk doc-space usage
dingtalk doc-space plan current
dingtalk doc-space plans list
```

**2. 権限系アクション**
```bash
dingtalk doc-space upgrade permission-check --output json
```

**3. 操作系アクション**
```bash
dingtalk doc-space upgrade --plan pro_100g --dry-run
dingtalk doc-space upgrade --plan pro_100g --confirm
dingtalk workflow create --type space-upgrade-approval
```

### Agentの実行フロー

1. **意図識別** — ユーザーの自然言語をモデルが分析、サブ問題に分解
2. **ツール決定** — Function Callingでモデルが適切なtoolを選択
3. **CLIマッピング** — ホストがtoolをCLIコマンドにマッピングして実行
4. **結果に基づく計画継続** — モデルが結果を見て次のステップを決定

> **toolはモデルに見えるエントリポイント、CLIはシステム内部の実行アクション**

## CLIがモデルに「理解」される3つの経路

1. **訓練時の知識** — ls、grep、curl、git statusなどの古典的コマンド
2. **Skills/ドキュメントの明示** — コマンドと使用法の事前定義
3. **ランタイム探索（--help）** — モデルがCLIのhelpコマンドを実行し、実行時にパラメータ構造を学習

## shellモード（スーパーツール）のパターン

一部のシステムは各CLIアクションを個別のtoolsとして声明せず、**単一の強力な汎用実行ツール**のみを暴露する：

```json
{
  "type": "function",
  "function": {
    "name": "shell",
    "description": "Execute a shell command"
  }
}
```

これはエンジニアリング意味論的に`eval`に近い。モデルはshell経由でCLIの`--help`を実行し、実行時にコマンド知識を学習する。

**メリット**: パラメータ知識を「プロンプト事前声明」から「ランタイム按需探索」へ移動
**デメリット**: 安定性が低く、セキュリティリスクが高い

## GUIの問題点

GUIは人間の習慣に適合して生まれた産物。情報量が大きく、常用機能一目了然。「指す・打つ」が可能。

しかし**AIがGUIを操作するのは非常に問題が多い**：
- UIは頻繁に変更される
- 現段階の技術では安定性が極めて悪い
- Computer-Use / browser-Useはまだ信頼性が不十分
- GUIの1回のクリックの裏には具体的なアクションが隠れている — AIにとっては「多すぎる」

AIの目標は原子的で、タスクは単一的。大きな情報量は不要。そこでCLIが登場する — これらのアクションを直接呼び出し可能な「コマンド」に再还原する。

## なぜCLIが重要になっているのか

GUIの各クリックがCLIでは以下のようになる：
```
calendar list --date tomorrow
message send --to zhangsan --text "会議は3時に変更"
doc export --input report.md --format pdf
```

GUIとCLIの本質的な違いはない — どちらも**ソフトウェア内部の能力を人間・スクリプト・Agentが直接呼び出せる標準アクションに変換する**もの。

プラットフォームが提供したいものが多すぎる → GUIソフトウェアの情報量は人間の受容限界を遥かに超える → 実際のところ、システムの20%以下の機能しか使用していない。

CLIは残り80%の不常用機能を記憶・処理してくれる。

## まとめ：三者の関係

| 概念 | 解決する問題 | 喩え |
|------|------------|------|
| **MCP** | 接入問題 | USBポート — ツールをシステムに接続 |
| **CLI** | アクション問題 | 実行層 — 能力を構造化・パラメータ化 |
| **GUI** | 人間の理解・確認問題 | 情報表示層 — 人間に最適化 |

> MCPが死なない理由：解決する問題（接入）は依然として存在する
> CLIが重要になる理由：Agentは天然、組み合わせ可能・パラメータ化可能なアクション層を必要とする

## GPT-5-Codexのローカル導入とSSHリモート開発

2026年4月、CLIエージェントパターンに関連する2つの重要な展開があった。

### Codexのローカルインストール（中国国内向け）

Juejin開発者「哪吒编程」が**GPT-5-Codexのローカルインストール手順**を公開。中国国内の開発者がVPNや海外決済手段なしで直接Codexを利用する方法を解説している。

- Cursor→Claude Code→Codexへの移行経験を持つ開発者が、最終的にCodexを主力に据えた
- ローカルインストールによりAPI経由での直接利用が可能
- 中国国内からのアクセス障壁を解消する実用的なアプローチ

📎 出典: [Juejin — Codexローカルインストール](https://juejin.cn/post/7554270339796336678) `[Tier-2]`

### Codex AppのSSHリモート開発機能追加

V2EXで「Codex Appが密かにSSHリモート開発機能を追加した」と報告された。

- リモートサーバーへの直接アクセスとコード編集が可能
- CLIエージェントパターンの重要な拡張：ローカルだけでなくリモート環境もカバー
- GUIに依存しない完全なテキストベースの開発フローの実現

📎 出典: [V2EX — Codex SSH機能](https://www.v2ex.com/t/1206760) `[Tier-1]`
