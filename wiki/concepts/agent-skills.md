# Agent Skills — AIエージェントのモジュール型能力システム

> **トレンド順位**: NEW（2026-04-18集計）
> **ソース**: juejin（掘金）を中心に急速に議論拡大中

## 概要

Agent Skills（技能包）とは、AIエージェントがロード・アンロード可能な**モジュール型の能力単位**である。2026年、[[claude-code]]をはじめとするコーディングエージェントの普及に伴い、Skillsは「エージェントにどう振る舞うかを教える知識・ルールの束」として、AI開発ワークフローの不可欠な構成要素となった。

具体的には、`CLAUDE.md` ファイル、`.cursorrules`、`.github/copilot-instructions.md` など、プロジェクトローカルに配置される設定・ルール・知識の集合体がSkillsに該当する。これらはエージェントのコンテキストに注入され、コーディング規約、テスト方針、レビュー基準、アーキテクチャパターンなどの「社内規定」としてエージェントの振る舞いを制御する。

> "2026年最值得学习的AI技能是Skills。Claude Code、龙虾(Lobster/Codex)、爱马仕(Hermes)、所有的Agent都依赖Skills"
> （2026年に最も学ぶ価値のあるAI技能はSkillsだ。Claude Code、ロブスター（Codex）、エルメス（Hermes）、全てのAgentがSkillsに依存している）
> — [万字干货！Agent Skills从入门到精通](https://juejin.cn/post/7628903339975540763)（掘金、沃垠AI）

## Skillsの定義と分類

### Skillとは何か

Skillは、エージェントの**ローカルな知識・ルール・ワークフローの束**である。[[mcp]]がエージェントの外部接続能力（「何にアクセスできるか」）を拡張するのに対し、Skillsはエージェントの内部的な振る舞い（「どう行動すべきか」）を定義する。

[[harness-engineering]]のExternalizationフレームワーク（arXiv 2604.08224）では、Skillsは**Memory**・**Protocols**と並ぶ外化メカニズムの一要素として位置づけられ、再利用可能な能力モジュールとして整理されている。

### Skillsの分類

中国語圏の実践記事を総合すると、Skillsは以下のカテゴリに大別される：

| カテゴリ | 内容 | 例 |
|---------|------|----|
| **コーディング規約系** | 言語・フレームワーク固有のスタイル・パターンを定義 | TypeScript命名規則、React Hooksルール、エラーハンドリング方針 |
| **テスト・品質保証系** | テスト戦略・カバレッジ基準・レビューチェックリスト | ユニットテスト必須化、E2Eテストパターン、コードレビュー基準 |
| **アーキテクチャ系** | プロジェクト構造・設計パターン・依存関係ルール | ディレクトリ構成、レイヤードアーキテクチャ、モジュール境界 |
| **ワークフロー系** | 開発プロセス・Git運用・CI/CDパイプラインのルール | ブランチ戦略、コミットメッセージ規約、デプロイ手順 |
| **ドメイン知識系** | 業務固有の用語・ロジック・制約条件 | API設計規約、データモデル定義、業務ルール |
| **振る舞い制御系** | エージェントの応答スタイル・思考プロセスの制御 | 回答形式、確認フロー、エスカレーション基準 |

## Skill vs MCP vs Function Calling

中国語圏で広く参照されている分類記事（109いいね、226スター）に基づき、Agent関連概念の階層と境界を以下に整理する。

```
Prompt（指示文）
  ↓ 自然言語による指示
Function Call（関数呼び出し）
  ↓ モデルが構造化された関数を呼び出す
Skill（技能包）
  ↓ ローカルな知識・ルールの集合体
MCP（Model Context Protocol）
  ↓ 外部ツール・サービスとの標準接続プロトコル
Agent（智能体）
  ↓ 上記全てを統合して自律的に動作するシステム
```

### 三者の比較

| 比較項目 | Skill（技能包） | MCP | Function Calling |
|---------|-----------------|-----|------------------|
| **本質** | ローカルな知識・ルール | 外部ツール接続プロトコル | モデルの関数呼び出し機構 |
| **範囲** | プロジェクト内の規約・パターン | 外部サービス・API全般 | 個別の関数・ツール呼び出し |
| **実行場所** | ローカル（モデルのコンテキスト内） | MCP Server経由（外部プロセス） | モデル→アプリケーション間 |
| **永続性** | ファイルとして永続的に保存 | サーバープロセスとして稼働 | リクエスト単位で一時的 |
| **役割の喩え** | 「マニュアル・社内規定」 | 「USB接続ポート」 | 「手を伸ばしてボタンを押す動作」 |
| **依存関係** | なし（テキストファイル） | MCP Server実装が必要 | モデルプロバイダのAPI仕様に依存 |

核心的な区別：**Skillsは「何を知っているか」**、**MCPは「何にアクセスできるか」**、**Function Callingは「何を実行できるか」**。三者は補完的な関係にあり、実務では併用される。

> 参照：[Prompt、Agent、Function Call、Skill、MCP，傻傻分不清楚？](https://juejin.cn/post/7614205951297732654)（掘金、苏三说技术、109いいね / 226スター）

## 実践事例

### 32 Skills + 8 MCPsの実践レポート

掘金で大きな反響を呼んだ記事「別再裸用 Claude Code 了！」（もうClaude Codeを素のまま使うな！）は、実際にテスト済みの**32個のSkills**と**8つのMCP Server**を体系的に紹介している。この記事は、Skillsを「裸」（未設定）の状態で使うのではなく、プロジェクト固有の知識で武装させることの重要性を強調している。

紹介されているSkillsのカテゴリ例：
- **コード品質系**: リファクタリングルール、型安全性チェック、パフォーマンス最適化パターン
- **ドキュメント系**: README自動生成、APIドキュメント、コメント規約
- **テスト系**: テスト駆動開発フロー、テストケース生成パターン
- **Git運用系**: コミットメッセージ規約、PRテンプレート、ブランチ戦略

> 参照：[别再裸用 Claude Code 了！32 個亲测Skills + 8 個 MCP](https://juejin.cn/post/7620060655607857178)（掘金、蝎子莱莱爱打怪）

### 日常運用の実態：「30個入れて毎日使うのは6個」

別の実践レポートでは、30個以上のSkillsをインストールしたものの、日常的に有効化しているのは**わずか6個**という実態が報告されている。これは以下の実践的教訓を示唆する：

1. **Skillsの過積載は非効率** — コンテキスト窓を無駄に消費し、エージェントの推論精度を低下させる
2. **タスク別のSkill切り替えが重要** — フロントエンド作業時とバックエンド作業時で有効化するSkillsを変える
3. **「必須6個」の厳選** — プロジェクト全体に通用する汎用Skillsの核心セットを特定すべき

この「30個中6個」という数字は、Skills運用の**成熟度モデル**を示唆している。初期の「とりあえず全部入れる」フェーズから、「本当に必要なものだけを厳選する」フェーズへの移行が、Skills活用の鍵となる。

> 参照：「我装了 30 多个 Claude Code Skill，每天真开的就 6 个」（掘金）

### 万字入門ガイド

## Claude Code Skillsエコシステム

### CLAUDE.mdファイル

[[claude-code]]におけるSkillsの中核実装は**`CLAUDE.md`ファイル**である。このMarkdownファイルは、プロジェクトのルートディレクトリまたはサブディレクトリに配置され、エージェントがセッション開始時に自動的に読み込むコンテキストとして機能する。

```
プロジェクトルート/
├── CLAUDE.md           ← プロジェクト全体のSkills
├── src/
│   └── CLAUDE.md       ← src配下固有のSkills
├── tests/
│   └── CLAUDE.md       ← テスト固有のSkills
└── ...
```

`CLAUDE.md`は階層的に配置でき、ディレクトリごとに異なるSkillsを定義できる。これにより、モノレポ内の異なるサブプロジェクトに対して、それぞれ適切なコンテキストを提供できる。

### 他のエージェントにおける同等概念

| エージェント | Skillsファイル | 特徴 |
|-------------|---------------|------|
| [[claude-code]] | `CLAUDE.md` | 階層的配置、自動読み込み |
| Cursor | `.cursorrules` | プロジェクトルート、単一ファイル |
| GitHub Copilot | `.github/copilot-instructions.md` | GitHub統合 |
| Codex（龙虾） | `AGENTS.md` | OpenAIのエージェント向け |
| Hermes（爱马仕） | 独自設定形式 | オープンソースフレームワーク |

### コミュニティでのSkills共有

中国の開発者コミュニティでは、効果的なSkillsの共有・流通が活発化している。掘金（Juejin）を中心に、「テスト済み（亲测）」のSkillsコレクションが多数のエンゲージメントを獲得しており、以下のパターンが観察される：

- **公開レシピ型**: 汎用的なSkillsをコピー＆ペーストで利用可能な形式で共有
- **ベストプラクティス型**: 特定のフレームワーク・言語向けのSkills設計パターンを解説
- **比較レビュー型**: 複数のSkillsを実際にテストし、効果を定量的・定性的に評価

## 中国コミュニティでの議論

### 急速な普及と体系化

2026年4月時点で、中国語圏の開発者コミュニティにおけるSkillsへの関心は爆発的に拡大している。その背景には以下の要因がある：

1. **[[claude-code]]の中国開発者への浸透** — Claude Codeが中国のプログラマーの間で主要な開発ツールとして定着し、その設定最適化への関心が高まった
2. **「素のまま使うな」という啓蒙** — 「别再裸用」（素のまま使うな）というメッセージが広く共感を得た。未設定のエージェントは能力の半分も発揮できないという認識の普及
3. **Skills共有文化の形成** — 有効なSkillsを共有・評価する文化がJuejin上で形成され、集合知による最適化サイクルが回り始めた

### 概念の混乱と整理の動き

Prompt、Agent、Function Call、Skill、MCPといった概念の乱立に対し、「傻傻分不清楚？」（区別がつかない？）という率直なタイトルの記事が109いいねを獲得したことは、コミュニティにおける**概念整理への強い需要**を示している。Skillsという概念自体が比較的新しいため、MCPやFunction Callingとの境界が不明確なまま議論が進む場面も多く、体系的な分類への取り組みが続いている。

### Skill vs MCPの境界議論

「什么是Skill以及和MCP的区别」（Skillとは何か、MCPとの違いは何か）という記事が政采云技術チームから公開され、両者の明確な区別が以下のように提示された：

- **Skill** = エージェントに「どう振る舞うか」を教える **知識**
- **MCP** = エージェントが「何にアクセスできるか」を拡張する **接続口**

この区別は掘金コミュニティで広く受け入れられ、[[mcp]]ページでも参照されている標準的な理解となっている。

## Harnessフレームワークにおける位置づけ

[[harness-engineering]]の枠組み（arXiv 2604.08224 "Externalization in LLM Agents"）では、Skillsは以下のように位置づけられる：

```
┌─────────────────────────────────┐
│           Harness               │
│  ┌───────┐  ┌────────┐         │
│  │Memory │  │Skills ★│         │
│  └───────┘  └────────┘         │
│  ┌───────────────────┐         │
│  │   Protocols       │         │
│  │  (MCP等の通信規約) │         │
│  └───────────────────┘         │
│         ┌─────┐                │
│         │ LLM │                │
│         └─────┘                │
└─────────────────────────────────┘
```

Skillsは**再利用可能な能力モジュール**として、MemoryやProtocols（[[mcp]]等）と並ぶ外化メカニズムの一要素である。Harnessはこれら全てを統合する最上位の実行環境・制御層として機能する。



## 「Prompt已死、Skill当立」パラダイムシフト（2026-04-28更新）

2026年初頭、中国AI開発者コミュニティで**「PromptからSkillへ」**の転換議論が活発化。Juejin開発者「isArray」が提唱したこの概念は、以下の変遷を指す：

### Prompt Engineeringの限界
- **属人化**: 優れたプロンプトは特定の開発者に依存
- **再利用性低い**: 似たタスクでも毎回プロンプトを再構築
- **品質不安定**: 小さな変更で出力が大きく変動
- **スケーラビリティ欠如**: チーム全体で共有・管理が困難

### Skill時代の到来
- **再利用可能**: 一度定義すれば複数プロジェクトで共有
- **バージョン管理**: GitでSkillsの履歴を追跡可能
- **チーム標準化**: 組織全体で統一されたSkillsを採用
- **自動検証**: Skillの実行結果をテスト可能

> 「继续堆 Prompt，真的不如早点学 Skill」
> （Promptを積み続けるより、早めにSkillを学んだ方が良い）
> — isArray, Juejin（62いいね・97スター）

### 中国コミュニティの反応
- 「Prompt已死、Skill当立」（Promptは死に、Skillが立つ）というスローガンが拡散
- Claude Codeコミュニティで特に支持が高い
- 既存のPrompt Engineering知識をSkill定義に体系化する動きが加速

> **出典**: Juejin — [继续堆 Prompt，真的不如早点学 Skill](https://juejin.cn/post/7598433254128205864) [T2]
