# AI Agentチーム・スワームパターン

> **概要**: 単一Agentの限界（コンテキスト膨張、タスク競合、リソースボトルネック）を、複数Agentの協調で解決する開発パターン。

## 背景と動機

2026年4月、Juejin開発者「yezannnnnn」が**Claude Codeを使用して4つのAIエージェントチーム**を構築し、協調開発が実際に機能することを証明した。

> 「我用Claude Code搭了个四个AI的团队，居然真的能协作开发（附项目地址）」
> （Claude Codeで4AIのチームを組んだら、本当に協調開発できた。プロジェクトURL付き）

この記事は163いいね・258スターを獲得し、中国開発者コミュニティで大きな反響を呼んだ。

## 単一Agentの致命的問題

### コンテキスト膨張

- 単一Agentは長期タスク中にコンテキストウィンドウが溢れる
- 過去の指示・中間成果物・エラー情報が混在し、推論品質が低下
- 最終的に「何をしていたか」を見失う

### タスク競合

- 複数のサブタスクを並行して処理できない
- 直列実行による効率低下
- 依存関係の管理が困難

## 4AIチーム協調パターン

### アーキテクチャ

```
┌─────────────────────────────────────┐
│         Claude Code (ホスト)        │
│                                     │
│  ┌─────────┐  ┌─────────┐          │
│  │ Agent 1 │  │ Agent 2 │ ...      │
│  │(PM/設計) │  │(実装A)  │          │
│  └─────────┘  └─────────┘          │
│  ┌─────────┐  ┌─────────┐          │
│  │ Agent 3 │  │ Agent 4 │          │
│  │(実装B)  │  │(テスト)  │          │
│  └─────────┘  └─────────┘          │
└─────────────────────────────────────┘
```

### 役割分担例

| エージェント | 役割 | 担当範囲 |
|---|---|---|
| **PM/設計Agent** | タスク分解、計画立案、成果物レビュー | 全体設計、要件定義 |
| **実装Agent A** | フロントエンド開発 | UI/UX、コンポーネント実装 |
| **実装Agent B** | バックエンド開発 | API、データベース、ビジネスロジック |
| **テストAgent** | テスト作成、バグ検出、品質保証 | ユニットテスト、統合テスト |

### 協調メカニズム

1. **タスクキュー**: PM Agentがタスクを分解し、各Agentに分配
2. **成果物共有**: 各Agentの出力を共通リポジトリで管理
3. **フィードバックループ**: テスト結果を実装Agentにフィードバック
4. **コンテキスト分離**: 各Agentが独立したコンテキストで作業

## 実装上の課題

### 1. コンテキスト管理

- 各Agent間のコンテキスト共有方法
- 最新状態の同期メカニズム
- 競合解決戦略

### 2. エージェント間通信

- タスク完了通知の方法
- エラー伝播の制御
- 依存関係の表現

### 3. リソース最適化

- 各Agentのトークン使用量の管理
- 並列実行数の制限
- コスト効率の確保

## 実測データ：多Agent分解の产出守恒律（2026-09-17追加）

掘金開発者「米小虾」（本文日付 2026-09-16、score 0）が、マルチエージェント設計文書に頻出する3つの定説（folklore：コンテキストが小さくなる／並列で速くなる／分担で質が上がる）を実測で検証した記事「拆给 8 个子智能体，只拿回 2 3 倍信息：多智能体分解的产出守恒律」を公開。**8個の子Agentに分解しても親が回収できる情報は単Agent比で約2.3倍止まり**という定量結果を「产出守恒律（産出保存則）」と名づけ、分解数を増やしても回収情報の総量には頭打ちがある（＝Agent数に見合ったリターンがない）と主張する。同ページが4月時点で記録してきた楽観的実証（yezannnnnn の4Agent協調成功例）に対する、**反証寄りの定量データ**として対になる。単一ソース・個人実測（ベンチマーク設計の詳細は本文プレビューのみで未確認）のため**未検証**だが、マルチエージェント設計の限界を数値で提示した初期事例として価値がある。

> 出典: Juejin — 米小虾「拆给 8 个子智能体，只拿回 2-3 倍信息：多智能体分解的产出守恒律」(https://juejin.cn/post/7686040694946791433)、収集: 2026-09-17

## 通信コストの計測：C2C（KV-Cache直転送）の「五つの死結」（2026-09-21追加）

掘金開発者「米小虾」（本文日付 2026-09-21、score 0、产出守恒律実測 09-17 と同一執筆者）が、マルチエージェント間の通信を Text-to-Text（T2T：A がテキストをデコードし B が入力として読む）から **KV-Cache をモデル間で直接受け渡しする通信（C2C）** へ置き換える論文を解説。C2C 側は 2.5× 加速を主張するが、解説者は**五つの死結（五つの行き止まり）**として実用化障壁を分解したとされる（T2T の三コスト＝デコード長・再読み込み・レイテンシの機構論的分解を含む）。09-17 の产出守恒律（分解数が増えても回収情報総量は約2.3倍で頭打ち）が**情報の総量**側の限界を示したのに対し、本記事は**エージェント間通信の搬送層**側の限界（KV-Cache 直転送がアーキテクチャ非依存に機能しない等の構造問題）を論じるもので、同じ執筆者によるマルチエージェント限界論の第二弾と読める。本文はプレビューのみ受領（五つの死結の内訳の詳細は未受領）。単一ソース・未検証。

> 出典: Juejin — 米小虾「多智能体还在"说话"：C2C 把 KV-Cache 直接传给另一个模型，2.5× 加速背后的五个死结」(https://juejin.cn/post/7687630810608533530)、収集: 2026-09-21 [T1・単一ソース・プレビューのみ・未検証]

## 今後の展開

マルチエージェント協調開発は、以下の方向に発展すると予想される：

1. **自動タスク分解**: AIが要件から自動的にタスクを分割
2. **動的エージェント構成**: タスクに応じて最適なAgent編成を自動選択
3. **分散実行**: 複数の物理マシンでAgentを並列実行
4. **自己最適化**: 実行結果から協調パターンを自動改善



### 実装パターン：ファイルシステム通信（2026-04-19更新）

Juejin開発者「yezannnnnn」の実装では、**ファイルシステムをAI間通信媒体**として使用する独自アプローチが採用された：

```
agentGroup/
├── max/          # 麦克斯 - プロジェクトマネージャー
│   ├── CLAUDE.md     # 役割定義と強制チェックポイント
│   ├── PERSONA.md    # AI人設
│   └── skills/       # PMスキルパック
├── ella/         # エラ - UI/UXデザイナー
├── jarvis/       # ジャービス - フルスタック開発者
├── kyle/         # カイル - テストエンジニア
└── shared/       # 共有オフィス
    ├── status.json       # チーム状態看板
    ├── notifications.json # AI間メッセージ
    ├── tasks/            # TODOリスト
    └── docs/             # 設計ドキュメント
```

**強制チェックポイントメカニズム**：
- 各AIのCLAUDE.mdに「鉄律強制流程」を定義
- タスク範囲確認→戦略読取→通知確認→タスク分解→Skill検査→実行選択→Git安全の7ステップ
- 物理実行必須：「頭で理解する」ではなく「実際にReadツールでファイルを読む」
- 自己監視プロトコル：プロセス違反検出時に自動修正

**Token節約効果**：
- 従来：200+ tokens（AIが自由に情報収集）
- 最適化後：50 tokens（Skill優先メカニズム）
- 節約率：**75%**
